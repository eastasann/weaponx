# PRD — weaponx

## 1. 概要

weaponx は、案件ごとに増え続けるスライドとドキュメントを管理するツール。資料を作った(登録した)時点で、「どの案件か」「何を参考にしたか」「どれの新しい版か」を事実として記録する。資料が増えても、「どれが最新で、何を参考にしたか」が一覧で分かり、迷わず開ける。

資料そのものは Google ドライブなど元の場所に置いたままにし、アプリは管理に徹する。Google ドキュメント・スライドの作成とコピーはアプリから行い、その操作のついでに参考資料と版が記録される。

画面・振る舞い・用語の詳細は `docs/design-spec.md`(以下 design-spec)が正。

## 2. 背景と目的

### 背景

- コンサル・営業・リサーチ職は、案件ごとに提案書・調査レポート・見積書などが増え続ける。ファイル名とフォルダ階層だけでは「この提案書の元ネタはどれか」「これの最新版はどれか」が分からず、何を読むべきか判断できない場面が多い
- ドライブの検索は個々のファイルを見つけるためのもので、資料どうしのつながりは示さない
- 散らかった後に関連を推測して描く方式(Phase 0 の構想)は、推測の誤りと本文の読み取りを伴う。Phase 1 で「作った時点で記録する」方式に見直した(`docs/brainstorm-notes.md`)
- 記録を人の手入力に頼ると続かない。アプリから作れば記録が手間なしに済むので、ドライブ連携を前提にした(design-spec 1.1)

### 目的

- 資料が増えても、案件を開けば最新版と、参考資料・版のつながりが一目で分かり、1クリックで開ける状態にする
- 記録の手間を「作る操作のついで」に吸収し、記録が続く状態にする
- まず作者自身が日常で使い続け、同じ職場の人にも広げる

## 3. ターゲットユーザーと課題

| ロール | ペルソナ | 課題 |
|--------|---------|------|
| 一般ユーザー(案件のオーナー・編集者) | 案件を回すコンサル・営業。週に数本の資料を作り、前の案件の資料を元に新しい資料を作ることが多い | 前の版・元にした資料を探すのに時間がかかる。同じ資料の版がフォルダに散らばり、どれが最新か・どれを客先に出したかを取り違える |
| 一般ユーザー(案件の閲覧者・後から入った人) | 案件に途中から参加したメンバー、上長 | どの資料を読めばよいか分からない。最新版がどれかを人に聞くしかない |
| 管理者 | 作者自身(職場で広げるときの窓口) | 使ってよい人を限定したい。辞めた人・外れた人を止めたい |

## 4. 主要機能(ユーザーストーリー)

優先度: Must = MVP に必須(この PRD のストーリーはすべて Must)。MVP の後のものは6章。

### 一般ユーザー(全員)として

| # | ストーリー | 優先度 |
|---|-----------|--------|
| U-1 | Google アカウントでログインし、同時にドライブの許可を与えたい。別の画面で連携する手間なく、すぐ資料を作れるようにしたいから | Must |
| U-2 | 参加している案件の一覧を、最終更新の新しい順に見たい。今動いている案件にすぐ入りたいから | Must |
| U-3 | 案件を開いたら、資料の最新版だけが並んだ表を見たい。読むべきなのはどの行かを迷わないため | Must |
| U-4 | 資料を選んだら、版・参考資料・この資料を参考にした資料を横パネルでたどりたい。元ネタと派生先を行き来するため | Must |
| U-5 | 表の行や横パネルから、資料を元の場所で1クリックで開きたい | Must |
| U-6 | 参加している全案件の資料を名前で横断検索したい。どの案件にあったか覚えていない資料を探すため | Must |
| U-7 | 表を資料名と種別で絞り込み、名前・更新で並べ替えたい | Must |
| U-8 | 版の変更メモとタグ(「提出」など)を見たい。最新版と客先に出した版の違いを一覧で分かるため | Must |
| U-9 | 表示言語を日本語と英語で切り替えたい | Must |
| U-10 | 新しい案件を作り、そのオーナーになりたい | Must |
| U-11 | スマホでも案件と資料を探して開きたい(変更はしない) | Must |
| U-12 | ドライブの許可が切れたら、その場で気づいて、もう一度連携したい | Must |

### 案件の編集者として

| # | ストーリー | 優先度 |
|---|-----------|--------|
| E-1 | アプリから Google ドキュメント・スライドを新しく作り、そのまま案件の資料として記録したい | Must |
| E-2 | 最新版から「新しい版を作る」で次の版を作りたい。版と参考資料が自動で記録されるので、手で整理しなくて済むから | Must |
| E-3 | ある資料から「これを元に作る」で別の資料を作り、同じ案件か別の案件に追加したい。何を元にしたかが自動で残るから | Must |
| E-4 | ドライブ以外にある資料や、使い始める前からある資料を、リンクを貼るかドライブのファイル選択画面で選んで登録したい | Must |
| E-5 | アプリの外で作った新しい版を、リンクで系列の次の版として登録したい | Must |
| E-6 | 資料を登録・編集するときに、参考資料を検索して選びたい(他の案件の資料も) | Must |
| E-7 | 版に変更メモとタグを付け、あとから直したい | Must |
| E-8 | 間違えて登録した版を削除したい(元のファイルは消さない) | Must |
| E-9 | 同じリンクの資料を二重に登録しそうになったら止めてほしい | Must |

### 案件のオーナーとして

| # | ストーリー | 優先度 |
|---|-----------|--------|
| O-1 | 許可済みの利用者を案件に招待し、役割(オーナー・編集者・閲覧者)を決めたい | Must |
| O-2 | メンバーの役割を変え、外したい | Must |
| O-3 | 案件名を変え、案件を削除したい | Must |

### 管理者として

| # | ストーリー | 優先度 |
|---|-----------|--------|
| A-1 | 使ってよい Google アカウントをメールで追加したい。許可した人だけが入れるようにするため | Must |
| A-2 | 利用者を停止・再開したい。停止する人が唯一のオーナーの案件があれば、その件数を知りたい | Must |
| A-3 | 管理者を付け外ししたい(管理者は常に1人以上) | Must |

## 5. 成功指標(KPI)

利用者が数人の自分用 MVP なので、アクセス解析は入れず、DB の記録・アプリのログ・作者の実感で測る。測り方は `docs/05_operation-runbook.md` 6章「KPI の測り方」。

| 指標 | 目標 |
|------|------|
| 作者の利用頻度(案件画面を開いた日数。アプリのログ) | リリース後4週間、平日の80%以上の日に使う |
| 記録の続き方: 新しく記録された版のうち、アプリから作ったもの(新しく作る・これを元に作る・新しい版を作る)の割合 | 60%以上(ドライブ連携を前提にした判断が効いているかの確認) |
| 変更メモの記入率: 2版目以降の版のうち、変更メモがあるものの割合 | 50%以上 |
| 職場への広がり: 作者以外で、4週間続けて毎週1回以上案件画面を開いた人(アプリのログ) | 2人以上 |
| 「どれが最新か」を人に聞いた・取り違えた回数(作者の記録) | リリース後4週間で0回 |

## 6. スコープ外

MVP で作らないものは2種類ある。

- 後で足すかもしれないもの: design-spec 9章「拡張候補」のすべて(各項目の理由と、足すきっかけは design-spec 9章が持つ)
- プロダクトとして持たないもの(方針として作らない):
  - 本文の保存と、関連の推測(design-spec 1.2。記録した事実だけを扱う)
  - 課金
  - 公開 API・外部のクライアント(API は画面専用)
  - リアルタイム更新(他の人の変更は再読み込みで反映する。design-spec 6.0.6 の後勝ち)
  - 版の結合(git の merge にあたる。Google ドキュメント・スライドに結合の仕組みが無いため)
